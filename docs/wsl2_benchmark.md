# Benchmark metrics on WSL2

The existing `WSL2` Make variable selects the collector. Native Linux retains
the benchmark container and qmassa. With `WSL2=true`, benchmark omits that
collector container and launches Windows Python through WSL interoperability.
This applies to registry and local-image runs. The application containers are
unchanged.

## Prerequisites

Install Python 3 on Windows and install the host dependencies in PowerShell:

```powershell
python -m pip install psutil pywin32
```

From WSL, verify that `python.exe` starts that same Windows Python. The Windows
Python installation must be available on WSL's `PATH`.
Windows Python must be able to read the repository through its `wslpath -w`
path. Linux virtualenv dependencies are still installed by the Make targets.

GPU collection requires Windows GPU Engine performance counters exposed by
the graphics driver. PDH queries use English counter names through
`AddEnglishCounter`. Missing counters are reported as unavailable; CPU,
memory, and disk collection can continue. No Linux GPU-device mount is needed
for the host metrics collector.

## Commands

Run these commands from the repository root in WSL:

```bash
make benchmark
make benchmark-stream-density
make consolidate-metrics
make plot-metrics
```

The Makefile detects and exports `WSL2` automatically; no extra argument is
required. `RESULTS_DIR` defaults to the repository's `benchmark` directory and
can be overridden on all targets. Plotting remains a separate `make plot-metrics`
step, which saves the image and attempts to open it. Viewer failure does not
invalidate the saved image.

## Output

| File | Contents |
| --- | --- |
| `windows_metrics.json` | Capture manifest: scenario, pipeline count, status, sample count, selected captures, unsupported metrics |
| `windows-metrics/<capture-id>.jsonl` | Timestamped CPU, memory, disk, and per-adapter GPU-engine samples |
| `windows_metrics_error.log` | Windows collector diagnostics |
| `metrics.csv` | Consolidated metrics, generated by `make consolidate-metrics` (also part of quickstart) |
| `plot_metrics.png` | CPU, memory, disk, and GPU graphs, generated by `make plot-metrics` |

Application pipeline logs and stream-density logs keep their existing formats.
WSL runs do not generate fake qmassa, sar, iotop, PCM, or NPU files. Reporting
ignores stale Linux hardware metrics when Windows reporting is selected.

CPU and memory are percentages for the **Windows host**, including other
applications. Disk values are host read/write throughput in MiB/s, derived
from byte-counter differences; they are not per-process iotop measurements.
GPU samples sum process counters for each physical engine, capped at 100%,
keeping adapters and engines separate. They are Windows engine names, not
Intel CCS/RCS counters or an isolated WSL-workload percentage.

Consolidation preserves the existing CSV keys: `CPU Utilization %`,
`Memory Utilization %`, `Disk Read MB/s`, and `Disk Write MB/s`. Capture disk
values are converted from MiB/s to decimal MB/s for the existing CSV convention.
Camera FPS, last-update, and latency extraction remains unchanged. Collector
source, status, and scenario metadata stays in the manifest, not in new CSV rows.

`NPU Utilization %`, `S0 Memory Bandwidth Usage MB/s`, and `S0 Power Draw W`
are `NA` because these measurements are unavailable. For each observed Windows
adapter, the existing six `GPU_<index>` engine/power keys are also `NA`: there
is no validated mapping to Intel CCS/RCS/VCS/VECS/BCS hardware counters. GPU
indices are zero-based positions in the sorted Windows adapter IDs for that
capture, not Linux DRM card numbers. With no observed adapter, the existing
generic `GPU Utilization %` key is `NA`.

Actual Windows GPU-engine measurements remain available in JSONL captures and
the graph under their Windows names. Missing measurements are never converted
to zero. Unsupported GPU counters produce an unavailable graph panel.

Normal benchmark collection starts after initialization. Stream-density
collection covers each FPS/latency measurement window, excluding memory probes,
startup, and shutdown. Each window has its own capture; reporting selects the
latest complete capture matching the returned pipeline count for each
container/target-FPS scenario. Other captures remain available for inspection.
If no matching capture exists, no different iteration is silently substituted.
The single-summary CSV uses the last selected scenario when multiple scenarios
exist and prints a warning; it does not average different scenarios together.
The graph shows each selected scenario separately.
The density algorithm and its Linux-memory OOM checks are unchanged.

A new benchmark resets the manifest while retaining older raw capture files.
Interrupted captures are marked failed and are not selected. Graceful shutdown
uses the collector's stdin; a timeout forces termination. Dependency or startup
errors fail the run; later collection failures are recorded and warned about.

## Validation

Linux tests cover counter aggregation, WSL gating, process cleanup, selected
density captures, native/WSL benchmark command paths, CSV generation, and PNG
generation using synthetic samples. A real Windows/WSL2 run is still required
to validate driver counters and Windows interoperability on the target machine.
